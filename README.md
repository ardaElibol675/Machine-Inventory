# machine-inventory

Know what is on your Debian/Ubuntu machine and why, rebuild it after a reinstall, and move it to another release or distribution: only the apps you pick, with their sources, config files and services.

- **`mi export`** takes a snapshot of the machine: apt (manual, user-added, history, local .debs), apt sources and keyrings, snap, flatpak, pip `--user`, VS Code extensions, GNOME extensions and dconf, dotfiles, your own systemd units, the `/etc` files you changed or added (secrets are never copied), `/opt` and `/usr/local`, and every git repository with its remote and branch.
- **`catalog.yaml`** is what you *want*, grouped into apps, with a reason for each. You curate it by hand or with the `/inventory` Claude Code skill.
- **`mi check`** runs health checks and shows the drift between snapshot and catalog: installed things no item claims, and catalogued things that are missing.
- **`mi restore`** asks group by group, then app by app, what to install, shows the full plan, and runs it.
- **`mi migrate`** and the `/migration` skill turn the inventory into a ready-to-install plan for another release or distribution.

Supported: Debian, Ubuntu and their derivatives (apt, snap, flatpak). Other package managers can be added as modules (`machine_inventory/modules/__init__.py`), other archives for `mi migrate check` in `machine_inventory/archives.py`.

## Install

Clone the tool anywhere and run the bootstrap script. It installs what `mi` needs (python3, python3-yaml, git, whiptail, curl) if missing:

```bash
git clone https://github.com/ardaElibol675/Machine-Inventory.git machine-inventory
```

```bash
cd machine-inventory && ./bootstrap.sh
```

For the Claude Code skills (`/inventory`, `/migration`), link them once per machine (again after moving the tool folder):

```bash
./mi install-skill
```

## Your two private repos

The tool is public; your data is not. It lives in two private git repositories of your own, on any git host, with any names you like. They are always cloned into the tool folder under fixed folder names, and the tool's own git ignores them:

```
machine-inventory/          the tool (public)
├── mi, bootstrap.sh, machine_inventory/, skills/, examples/, tests/
├── inventory/              private repo #1: facts and catalog of your current machine
│   ├── config.yaml         your settings (which dotfiles, dconf paths, ...)
│   ├── catalog.yaml        what you want, and why
│   ├── INVENTORY.md        generated by `mi render`
│   ├── README.md           written by /inventory: what is in here, how to restore it
│   ├── snapshot/           generated by `mi export`
│   ├── notes/, reports/    pitfalls and scan log (used by /inventory)
└── migration/              private repo #2: one folder per target release
    ├── README.md           written by /migration: how to install each target
    └── <ID>-<VERSION_ID>/  e.g. debian-13, ubuntu-26.04
```

Create the inventory repo on a new setup:

```bash
./mi init
```

```bash
git -C inventory init
```

Then add a private remote (`git -C inventory remote add origin <your-inventory-repo>`) and push whenever you like. Or, if you already have one, clone it:

```bash
git clone <your-inventory-repo> inventory
```

The migration repo is only needed when you move to another release. Create it the same way (`mkdir migration && git -C migration init`, then a private remote), or clone it:

```bash
git clone <your-migration-repo> migration
```

The inventory contains file names, repository URLs and dotfiles. Keep both repos private. Secrets from `/etc` are never copied, but check your dotfiles before you push.

## Daily use

Edit `inventory/config.yaml` (which dotfiles, dconf paths, home layout, ...; every key is documented in `examples/inventory/config.yaml`), then:

```bash
./mi export && ./mi check
```

Put the uncatalogued things into `inventory/catalog.yaml` (the format is documented at the top of `examples/inventory/catalog.yaml`), then regenerate `inventory/INVENTORY.md`:

```bash
./mi render
```

`mi export` is read-only for the system and idempotent: running it twice gives no diff, so every line in `git diff` is a real change. If a fact cannot be collected (for example apt cannot read its lists), the previous file is kept and a warning is printed.

With Claude Code, type `/inventory` instead. The skill exports, investigates every warning, catalogues new packages (asking you when the purpose is unclear), updates `INVENTORY.md`, the scan log and `inventory/README.md`, and suggests fix-up commands. It never installs anything and never runs git: committing and pushing is yours.

## Restore on a new machine

Same release as the inventory (a reinstall, or a second machine):

```bash
git clone <tool-repo-url> machine-inventory && cd machine-inventory
```

```bash
git clone <your-inventory-repo> inventory
```

```bash
./bootstrap.sh
```

```bash
./mi restore --dry-run
```

```bash
./mi restore
```

The dry run walks you through the wizard and prints the plan; nothing runs. The second command does the same and runs the plan after you confirm. In Claude Code, `/inventory restore` guides you through it.

Non-interactive use:

```bash
./mi catalog                                   # groups and items (* default, ! not compatible)
./mi restore --dry-run --select dev,vlc        # group ids pick their default items; item ids pick one item
./mi restore --dry-run --all-defaults
./mi restore --dry-run --all-defaults --os-release tests/fixtures/ubuntu-24.04   # pretend another target
```

The plan runs in this order: apt sources and keys → apt → snap → flatpak → VS Code → pip → git clones → dotfiles → systemd units → `/etc` files → GNOME extensions (downloaded from extensions.gnome.org for the running GNOME Shell and enabled; they load after the next login) → dconf → post commands. Manual steps (licence sign-ins, checks after a reboot) are printed at the end. Existing files that differ are kept as `<file>.bak-YYYYMMDD`.

Failures:

- **Package installs never stop the run.** apt packages that the target's repositories do not have are skipped with a warning; if the rest fails as a batch, each package is tried on its own. A failing snap, flatpak, VS Code extension or pip package is skipped too. Everything skipped is listed at the end, and `mi restore` exits with code 3.
- **Anything else** (adding a source, writing a config file, enabling a unit) makes `mi` stop and ask: retry, skip, or abort, because later steps may depend on it. `--keep-going` skips those as well, without asking.

## Migrate to a new machine

Another release or another distribution. Restoring the inventory there directly would only offer the items marked compatible, and some problems never show up as compatibility at all: renamed packages, repositories without a build for the new release, desktop and session changes, your own projects built for a stack the target lacks. A migration target settles all of that on the old machine first.

On the **old machine**, in Claude Code:

```
/migration Debian 13
```

The skill writes the target's os-release file (checked against official sources), runs `mi migrate init`, reviews every item against the differences between the two releases, researches alternatives, and lets you decide what to keep, adapt, replace, drop or add. The result is `migration/<ID>-<VERSION_ID>/`: an ordinary `mi` data folder (catalog, config, and copies of only the files its items need, already adapted) plus `migration.yaml` with one decision and reason per inventory item, and `migration/README.md` with the install steps. The skill never scans the machine and never changes the inventory. Review it, then commit and push the migration repo.

Without Claude Code, the same building blocks:

```bash
./mi migrate init <target-os-release-file>   # creates migration/<ID>-<VERSION_ID>/ (keep / replace / pending)
./mi migrate check <ID>-<VERSION_ID>         # open decisions, missing files, packages the target lacks
./mi migrate render <ID>-<VERSION_ID>        # INVENTORY.md with the decisions table
```

`mi migrate check` downloads the target's package indexes (cached in `~/.cache/machine-inventory/`); `--offline` skips that part.

On the **new machine**:

```bash
git clone <tool-repo-url> machine-inventory && cd machine-inventory
```

```bash
git clone <your-migration-repo> migration
```

```bash
./bootstrap.sh
```

```bash
./mi migrate <target> --dry-run
```

```bash
./mi migrate <target>
```

`mi migrate <target>` is `restore` for `migration/<target>/` instead of `inventory/`, with the same options (`--dry-run`, `--select`, `--all-defaults`, ...). `mi migrate catalog <target>`, `mi migrate render <target>` and `mi migrate <target> --dry-run` judge items against the target's os-release, so you can dry-run a target on the old machine too. A real restore refuses to run on any release other than the target, and `export` and `check` refuse to run on a migration target (it is a plan, not facts about a machine). After the restore, start a fresh inventory on the new machine with `./mi init`, or clone your inventory repo and let `/inventory` catch it up.

## Compatibility rules

Items can say where they work; the wizard hides the rest (`--include-incompatible` shows them):

- `compat: {ubuntu: ["22.04", ">=26.04"], debian: ["13"]}` limits an item to releases: exact versions or ranges (`>=`, `<=`, `>`, `<`). `ubuntu: []` means any Ubuntu, derivatives included (`ID_LIKE`). Use it for apt sources that name a suite, packages a release dropped, and settings that only make sense on one desktop version.
- `requires_paths: [/sys/class/power_supply/BAT*/charge_control_end_threshold]` limits an item to hardware where every glob matches. It is checked on the machine being restored, never when preparing a migration.
- `replaces: [<item id>]` marks an item as the alternative of another one, for example the distro build of an app whose upstream repository only exists for the older release. `mi migrate init` then decides the old item as `replace` by itself.

### systemd units are templates

`mi export` saves your own units with your home directory replaced by `@HOME@` and `User=`/`Group=` lines naming you replaced by `@USER@`/`@GROUP@`. Restore fills these in for the user running it, so a unit pointing at `~/Services/app` works after a reinstall with a different username.

## Development

```bash
python3 -m unittest            # uses examples/inventory, a fake snapshot and fake os-release files
```

Contributors to the public tool: put your name, handles and private project names into `private_terms` in `inventory/config.yaml`, and run this before every push. It fails if a home path, your username, git name or email, or a private term appears anywhere outside `inventory/` and `migration/`:

```bash
scripts/check-public.sh
```

A module (`machine_inventory/modules/*.py`) may define `collect(ctx, snap)`, `check(ctx, rep)`, `drift(ctx, catalog, rep)` and `steps(ctx, catalog, items)`; see `modules/base.py`. Migration targets are built in `machine_inventory/migrate.py`; package archives of other distributions are registered in `machine_inventory/archives.py`.

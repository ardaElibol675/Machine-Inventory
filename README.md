# machine-inventory

Know what is on your Debian/Ubuntu machine and why, and rebuild it after a reinstall: only the apps you pick, with their libraries, sources, config files and services.

- **`mi export`** takes a snapshot of the machine: apt (manual, user-added, history, local .debs), apt sources and keyrings, snap, flatpak, pip `--user`, VS Code extensions, GNOME extensions and dconf, dotfiles, your own systemd units, the `/etc` files you changed or added (secrets are never copied), `/opt` and `/usr/local`, and every git repository with its remote and branch.
- **`catalog.yaml`** is what you *want*, grouped into apps, with a reason for each. You curate it (by hand, or with the `/inventory` Claude Code skill).
- **`mi check`** runs health checks and shows the drift between snapshot and catalog: installed things no item claims, and catalogued things that are missing.
- **`mi restore`** asks group by group, then app by app, which items to install, shows the full plan, and runs it.

The tool is public; your data is not. Your inventory lives in `data/`, a separate private git repository inside the tool folder (ignored by the tool's own git).

```
machine-inventory/          this repo (public)
├── mi                      CLI (Python 3 + PyYAML)
├── machine_inventory/      package; one module per source in modules/
├── bootstrap.sh            installs python3, python3-yaml, git, whiptail, curl on a fresh system
├── skills/inventory/       the /inventory Claude Code skill
├── examples/data/          documented sample config.yaml and catalog.yaml
├── scripts/check-public.sh fails if personal data leaked into this repo
├── tests/
└── data/                   YOUR private repo (own .git)
    ├── config.yaml         personal settings
    ├── catalog.yaml        what you want, and why
    ├── INVENTORY.md        generated by `mi render`
    ├── snapshot/           generated by `mi export`
    ├── notes/pitfalls.md   lessons learned on your machine
    └── reports/            scan log, cleanup notes
```

Supported: Ubuntu and Debian (apt, snap, flatpak). Other package managers can be added as modules (see `machine_inventory/modules/__init__.py`).

## Start

Clone it anywhere and `cd` into it:

```bash
git clone <this-repo-url> machine-inventory && cd machine-inventory
./bootstrap.sh
./mi init            # creates data/ from examples/data
```

Edit `data/config.yaml` (which dotfiles, dconf paths, home layout, ...), then:

```bash
./mi export          # snapshot this machine into data/snapshot
./mi check           # health + "uncatalogued" list
```

Put the uncatalogued things into `data/catalog.yaml` (the format is documented at the top of `examples/data/catalog.yaml`), then `./mi render` to regenerate `data/INVENTORY.md`.

`mi export` is read-only for the system and idempotent: running it twice gives no diff, so every line in `git diff` is a real change. If a fact cannot be collected (for example apt cannot read its lists), the previous file is kept and a warning is printed, so a broken tool never looks like "everything was removed".

## Keep it current

Quick, script only:

```bash
./mi export && ./mi check --quiet
```

Full, with Claude Code: type `/inventory`. The skill exports, investigates every warning, catalogues new packages (asking you when the purpose is unclear), updates `INVENTORY.md` and the scan log, and gives you fix-up commands. It never installs anything and never runs git.

Install the skill once per machine (re-run it if you move the tool folder):

```bash
./mi install-skill
```

## Restore on a new machine

```bash
git clone <this-repo-url> machine-inventory && cd machine-inventory
git clone <your-private-data-repo> data
./bootstrap.sh
./mi restore --dry-run      # click through the wizard, see the plan, nothing runs
./mi restore                # the same, then runs the plan after you confirm
```

The wizard hides items whose `compat` does not match the target system (`--include-incompatible` shows them). Non-interactive use:

```bash
./mi catalog                                   # groups and items (* default, ! not compatible)
./mi restore --dry-run --select dev,vlc        # group ids pick their default items; item ids pick one item
./mi restore --dry-run --all-defaults
./mi restore --dry-run --all-defaults --os-release tests/fixtures/ubuntu-24.04   # pretend another target
```

The plan runs in this order: apt sources and keys → apt → snap → flatpak → VS Code → pip → git clones → dotfiles → systemd units → `/etc` files → dconf → post commands. Manual steps (downloads, licences) are printed at the end. Existing files that differ are kept as `<file>.bak-YYYYMMDD`. If a command fails, `mi` stops and asks: retry, skip, or abort. In Claude Code, `/inventory restore` walks you through the same flow and runs it only after you approve the plan.

## Publishing

Tool repo (public):

```bash
scripts/check-public.sh                 # must print OK: no home paths, usernames, emails, private terms
git init -b main && git add -A && git commit -m "machine-inventory"
git remote add origin <public-remote> && git push -u origin main
```

Data repo (private, it contains your file names, emails in dotfiles, repo URLs):

```bash
cd data
git init -b main && git add -A && git status    # check that only expected files are there
git commit -m "inventory" && git remote add origin <private-remote> && git push -u origin main
```

Add your name, handles and private project names to `private_terms` in `data/config.yaml`; `check-public.sh` greps the tool repo for them.

## Development

```bash
python3 -m unittest            # tests use examples/data and fake os-release files
scripts/check-public.sh
```

A module (`machine_inventory/modules/*.py`) may define `collect(ctx, snap)`, `check(ctx, rep)`, `drift(ctx, catalog, rep)` and `steps(ctx, catalog, items)`; see `modules/base.py`.
